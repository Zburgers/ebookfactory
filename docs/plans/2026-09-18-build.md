# Ebook Factory implementation plan

**Goal:** deliver the personal ebook system defined in DESIGN.md, with >80/100 evidence-backed completion and all mandatory gates.

**Architecture:** FastAPI owns PostgreSQL state and scoped tools; a TypeScript Pi supervisor runs chat and rootless production tasks; a reused React component stack supplies the dashboard. Telegram connects to the same conversation, and immutable manuscript revisions feed validated exports.

**Tech stack:** Python/FastAPI/SQLAlchemy/Alembic, PostgreSQL, TypeScript/Pi SDK, React/Ant Design, rootless Podman, maintained converters/validators. Pin tested versions; no new queue service.

For the Luna lead: execute packets in dependency order using AGENTS.md. File paths below are intended implementation files, not pre-existing code. Each packet: inspect -> minimal implementation -> focused behavior check -> independent critique -> repair -> local commit -> status/ledger update. Do not ask the owner to choose routine implementation details.

## P00 — capability and target discovery

Files: `scripts/doctor.sh`, `docs/CAPABILITIES.md`, `evidence/P00/`.

1. Verify actual paths, Pi/Codex versions, installed adapters, Podman rootless operation, converters, available ports, PostgreSQL listener identity and owner. Do not print environment values or auth contents.
2. Confirm exact DB target/role with owner before changes. Record token/chat IDs as configured/not configured only.
3. Spike one actual Pi SDK call using existing auth, capture session events and usage. Verify custom model endpoint configuration using a local protocol fixture and a configured live endpoint where available.
4. Spike host Pi model gateway from a restricted container with no host credentials mounted; verify refresh and error forwarding. Spike Codex image artifact creation and quota reads. Record unsupported capabilities explicitly.
5. Record installed versions and capability evidence. Pin the runtime that worked; no speculative SDK API calls in production.

Acceptance: artifact-backed capability matrix; no claims based only on catalog listing. Dependencies: none. Independent scaffolding work may continue while owner supplies DB/Telegram inputs.

## P02 — durable jobs and events

Files: `apps/api/app/jobs.py`, `apps/api/app/events.py`, `apps/api/app/models.py`, `apps/api/tests/test_recovery.py`, worker `src/supervisor.ts`.

Implement atomic approval+enqueue, dedupe, claim/lease/fencing, checkpoint, retry/blocked states, pause/cancel epochs, event replay and outbox. Add worker claim/heartbeat APIs and small supervisor loop.

Acceptance: two concurrent claims produce one owner; crash/restart resumes accepted checkpoints; stale completion rejected; duplicate approval produces one run; event replay does not restart jobs. Run these against real PostgreSQL. Depends P01.

## P03 — Pi sessions, provider settings and scoped tools

Files: worker `src/pi.ts`, `src/providers.ts`, `src/tools.ts`, `src/model-gateway.ts`; API `app/providers.py`, `app/conversations.py`, `app/tools.py`; contracts `tools.schema.json`.

Acceptance: a real dashboard-configured provider answers, persists across restart, and executes a scoped tool; invalid cross-project context rejected; model switch reflected in subsequent usage; unrelated global configuration unchanged. Depends P01/P02; P00 proves API feasibility.

## P04 — execution sandbox

Files: `infra/podman/Containerfile`, worker `src/sandbox.ts`, API artifact registration, `scripts/check-isolation.sh`.

Implement fixed-image rootless run creation, private workspace, resource limits, constrained network gateway, labelled reconciliation and precise teardown. Orchestrator requests execution through a tool; trusted supervisor creates containers. No per-chat container. Validate imports before committing artifacts.

Acceptance: host sentinel file cannot be read/written, unrelated LAN destination denied, allowed gateway succeeds, traversal/symlink artifact rejected, cancellation terminates owned task, restart cannot double-publish, unrelated container survives cleanup. Depends P02/P03.

## P05 — autonomous book production

Files: worker `src/production.ts`, `packages/prompts/{orchestrator,nonfiction,fiction,review}.md`, API `app/documents.py`, `app/reviews.py`.

Implement brief -> research/knowledge -> outline -> sections -> editorial review/repair -> draft review. Use bounded delegated sessions, stored input revisions and budgets. Sequential dependent drafting by default; parallelize independent research/review. Implement retrieval context packets and change impact/invalidation, not full-book prompt concatenation. Main orchestrator alone requests decisions.

Acceptance: real short nonfiction and fiction fixtures complete with chapter continuity, persisted source/knowledge records and no hidden child approvals; owner revision yields a new draft without losing earlier work. At least one real production run is disconnected/restarted mid-task. Depends P02–P04.

## P07 — usage and quota dashboard

Files: worker `src/usage.ts`, API `app/usage.py`, quota adapters, dashboard Usage page.

Implement per-call normalized usage, dedupe/finalization/corrections, task rollups, actual versus estimated cost, quota snapshots and stale/unavailable states. Include retries, child agents, failed calls and image calls when supplied. Snapshot provider pricing versions; preserve unknowns.

Acceptance: captured stream replay doesn't double-count, totals reconcile to calls, account snapshots are not misattributed to a book, real Codex/Copilot capability outcomes shown. Missing provider fields reduce detailed quota rubric points, not honesty. Depends P03/P06; implement usage capture before production acceptance.

## P08 — art and publishing

Files: worker `src/codex-art.ts`, API `app/exports.py`, export templates, `scripts/validate-package.sh`, publishing report schema.

Acceptance: real image file through Pi-controlled tool; render/open all formats; EPUBCheck clean; cover criteria pass; metadata matches manuscript; Kindle preview performed or explicitly pending. No Amazon upload. Depends P04/P05/P06 and image spike P00.

## P09 — Telegram

Implement one allowed bot/chat, persistent polling offset, same conversation routing, commands and revision-bound approvals, milestone notifications and private artifact delivery. Use supplied token safely.

Acceptance: actual allowed chat sends idea/status, dashboard sees it, approval replay doesn't duplicate run, wrong sender rejected, reconnect resumes, outgoing failure retries. Mock-only evidence cannot satisfy the live gate. Depends P02/P03/P06; can parallelize P08 after contracts stabilize.
